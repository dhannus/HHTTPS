### [S2] [Performance] server/email.js:L388-398 — Verbrauchte `email_verifications`-Zeilen werden nie gelöscht; die Tabelle wächst mit jeder erfolgreichen E-Mail-Verifikation unbegrenzt und die Lookup-Queries laufen ohne Index
**Begründung:** `sendVerificationEmail` legt pro Versand eine Zeile in `email_verifications` an (L388-398). Der Konsum läuft über `UPDATE … SET used = TRUE` (`getAndConsume`, `getAndConsumeByCode`, `invalidateForSession` in db.js L335-365) — die Zeile bleibt stehen. Der einzige Aufräumpfad ist `cleanup_expired()` in sql/schema.sql L203:
```sql
DELETE FROM email_verifications WHERE expires_at < NOW() AND used = FALSE;
```
Jede erfolgreich bestätigte Verifikation (`used = TRUE`) und jede durch Re-Send invalidierte Zeile (`invalidateForSession`, ebenfalls `used = TRUE`) ist damit dauerhaft von der Löschung ausgenommen; einen weiteren `DELETE FROM email_verifications` gibt es im Repo nicht (grep). Gleichzeitig filtern die Hot-Path-Queries aus AP3 auf Spalten ohne Index: `verifyEmailCode` (email.js L777 → `WHERE code = $1 AND session_id = $2`) und `/hhttps/email/send` → `invalidateForSession` (`WHERE session_id = $1 AND used = FALSE`). Indizes existieren nur auf `expires_at` und `email` (schema.sql L118-119); `code` wurde per `ALTER TABLE … ADD COLUMN` (db.js L376) ohne Index nachgerüstet.
**Auswirkung:** Da die E-Mail-Bestätigung der verpflichtende erste Schritt jedes Sign-ins ist, wächst die Tabelle linear mit der Zahl aller je durchgeführten Anmeldungen. Jeder `/hhttps/email/send` und jeder `/hhttps/email/confirm-code` macht dann einen Seq-Scan über alle Altzeilen (Update-Statement mit Zeilen-Locks), dazu Autovacuum-/Index-Bloat auf `email_verifications_email_idx`. Der Effekt ist heute (kleine Nutzerzahl) unsichtbar und wird schleichend zur Latenz auf dem Kern-Login-Pfad; außerdem bleiben `sha256(email)`-Hashes unbegrenzt liegen (Datensparsamkeit, hier nur als Nebeneffekt genannt).
**Empfehlung:** In `cleanup_expired()` das `AND used = FALSE` entfernen (verbrauchte Zeilen nach Ablauf ebenfalls löschen) — Owner AP6, Auslöser hier. Zusätzlich `CREATE INDEX … ON email_verifications(session_id)` (deckt `invalidateForSession` und `getAndConsumeByCode`) anlegen; optional `code` in den Index aufnehmen. Kurzfristig kann `bindSessionToEmailAnchor` die verbrauchte Zeile direkt löschen statt sie nur zu markieren.

### [S3] [Performance] server/email.js:L145-162 — Pro Mail wird ein neuer SMTP-Transport ohne Timeouts erzeugt; `/hhttps/email/send` blockiert bis zur SMTP-Antwort (Default bis zu 2 min Connect / 10 min Socket)
**Begründung:** `createTransport()` wird bei jedem Versand neu aufgerufen (L403, L498, L553, L602, L725, L871) und baut ohne `pool: true` für jede Mail eine neue TCP+STARTTLS-Verbindung inkl. AUTH auf. Es sind keine `connectionTimeout`/`greetingTimeout`/`socketTimeout` gesetzt (L147-154), nodemailer-Defaults sind 2 min / 30 s / 10 min. Im Request-Pfad `/hhttps/email/send` (server.js L2869) wird `await transporter.sendMail(...)` (L414) synchron abgewartet; erst danach wird der E-Mail-Kontext geparkt (server.js L2871-2875). Im Fallback-Zweig ohne SMTP-Konfiguration läuft zusätzlich bei jedem Versand `fs.existsSync` (L158) zweimal auf dem Event-Loop.
**Auswirkung:** Bei einem langsamen oder hängenden SMTP-Relay hält jeder Send-Request einen offenen HTTP-Request (nginx-Upstream, Express-Slot) minutenlang; die Session-TTL von 15 min (server.js L2695, L2736) läuft währenddessen weiter, sodass der Nutzer nach der Antwort ggf. bereits eine abgelaufene Session hat. Pro Mail ein kompletter TLS-Handshake plus AUTH erhöht die Latenz des Sign-in-Starts um typ. 300–1500 ms und die Last auf dem Relay (Strato/Brevo begrenzen Verbindungen pro Minute).
**Empfehlung:** Transporter modulweit einmal erzeugen (lazy, gecacht) mit `pool: true, maxConnections: 2–5` und expliziten Timeouts (`connectionTimeout: 10_000, greetingTimeout: 10_000, socketTimeout: 30_000`); den `existsSync`-Check einmalig beim ersten Aufruf durchführen. Optional den Request per `Promise.race` mit einem Timeout beantworten (503 `email_transport_unavailable`).

### [S4] [Performance] server/server.js:L2573 — `db.sessions.delete` existiert nicht; die vorherige Session wird beim Passkey-Merge nie gelöscht und lebt bis zum TTL-Ablauf weiter
**Begründung:** `sessions` in db.js (L147-237) exportiert `create/get/update/incrementEmailsSent/count/_normalize`, aber kein `delete` (grep `async delete` in db.js: nur challenges, tokens, refreshTokens, webhooks). Der Aufruf
```js
try { await db.sessions.delete(priorId); } catch (e) {}
```
wirft einen `TypeError`, der stillschweigend verschluckt wird. Der Kommentar in L2558-2566 („delete the old session so the user keeps exactly ONE active session“) beschreibt ein Verhalten, das nicht eintritt.
**Auswirkung:** Pro Passkey-Login nach E-Mail/GitHub/EUDI bleiben zwei aktive Session-Zeilen (bis 30 min) bestehen; `db.sessions.count()` (Stats) zählt doppelt. Das Wachstum ist durch die TTL und `cleanup_expired()` begrenzt — performanceseitig gering, aber der Aufruf ist toter Code mit falscher Annahme (Überschneidung mit Dimension Korrektheit; dort ggf. höher bewerten, da die alte Session nach dem Merge weiter nutzbar bleibt).
**Empfehlung:** `sessions.delete(sessionId)` in db.js ergänzen (`DELETE FROM sessions WHERE session_id = $1`) und den leeren `catch` durch ein Log ersetzen, damit ein solcher Fehler nicht erneut unbemerkt bleibt.

### [S4] [Performance] server/server.js:L656-666 — `issueAccessToken` und alle Session-/Verifikations-Pfade schreiben sequentiell auf eine einzige `stats`-Zeile (Hot-Row)
**Begründung:** `issueAccessToken` führt `db.tokens.create` (L656) und `db.stats.increment('tokens_issued')` (L666) nacheinander aus, obwohl beide unabhängig sind. `stats.increment` ist ein `INSERT … ON CONFLICT DO UPDATE SET value = stats.value + $2` (db.js L1321-1327) — jeder Aufruf nimmt ein Row-Lock auf derselben Zeile. Dieselbe Zeile `verifications` wird zusätzlich in `/hhttps/session/email/start` (L2735), `/hhttps/session/start` (L2790), `webauthn/register/finish` (L2500) und `webauthn/auth/finish` (L2593) inkrementiert; `/hhttps/token/refresh` (L2628-2640) landet über `issueAccessToken` auf `tokens_issued`.
**Auswirkung:** Unter gleichzeitiger Last serialisieren sich alle Login-/Refresh-Requests auf zwei Zeilen-Locks in `stats`; bei den heutigen Volumina messbar irrelevant, bei Lastspitzen (z. B. viele Refreshes zur vollen Stunde nach 1 h `ACCESS_TTL`) wird der Zähler zum Engpass. Reine Zähler sollten den Request nicht verlängern.
**Empfehlung:** `stats.increment` nicht awaiten (fire-and-forget mit `.catch(console.error)`) oder in-memory sammeln und periodisch flushen; mindestens `Promise.all([db.tokens.create(...), db.stats.increment(...)])`.

### [S4] [Performance] server/server.js:L2606-2660 — `/hhttps/token/refresh` macht fünf sequentielle DB-Roundtrips ohne eigenes Rate-Limit; `credentials.get` liefert nur `deviceType`
**Begründung:** Reihenfolge: `revokedTokens.has` (L2613) → `refreshTokens.get` (L2615) → `credentials.get` (L2618) → `tokens.create` + `stats.increment` (via `issueAccessToken`, L2628). `revokedTokens.has` und `refreshTokens.get` sind voneinander unabhängig; `credentials.get` wird nur für `cred?.deviceType || 'unknown'` (L2635) benötigt. Der Endpunkt hängt nur am globalen Limit (300/min pro IP, L420), jeder Aufruf legt eine neue `tokens`-Zeile mit 1 h TTL an (L93).
**Auswirkung:** ~5 Roundtrips (≈ 3–8 ms lokal, mehr bei Netz-DB) pro Refresh, obwohl 2–3 reichen; ein Client, der bei jedem Seitenaufruf refresht, kann bis zu 300 Token-Zeilen/min pro IP erzeugen, die bis zum Cleanup (alle 5 min, L714) liegen bleiben. Kein Ausfallszenario, aber unnötige Last auf dem meistgenutzten Pfad nach dem Login.
**Empfehlung:** `Promise.all([db.revokedTokens.has(jti), db.refreshTokens.get(jti)])`; `deviceType` beim Ausstellen des Refresh-Tokens in den signierten Claims mitführen (wie `pseudonym`/`emailDomain`, L684-693) und `credentials.get` entfallen lassen; ein moderates Limit (z. B. `rl(60, 15*60_000)`) setzen.

### [S4] [Performance] server/server.js:L485-514 — Die Identity-Cookie-Middleware verifiziert das ES256-JWT bei jedem Request, auch für alle statischen Assets
**Begründung:** Die Middleware ist vor `express.static` (L519) registriert und ruft bei vorhandenem Cookie `verifyToken` (L491) auf: `jwt.decode(…, {complete:true})` + `jwt.verify` (keys.js L164-173) = zweimal Base64/JSON-Parsen plus eine ECDSA-P-256-Verifikation pro Request. Das Ergebnis wird nur für die HHTTPS-Header der Antwort genutzt; für `.js/.css/.png` ist es wertlos.
**Auswirkung:** ~0,1–0,3 ms CPU pro Asset-Request auf dem Event-Loop; eine Seite mit 20 Assets kostet ~2–6 ms zusätzlich pro eingeloggtem Besucher. Kein Engpass, aber vermeidbare Grundlast auf jedem Request des Issuers.
**Empfehlung:** Die Verifikation auf Dokument-/API-Requests beschränken (z. B. `req.accepts('html')` bzw. Pfad-Prefix `/hhttps/`), oder das Verifikationsergebnis für die Cookie-Lebensdauer in einem kleinen LRU (Key: Token-Hash, TTL ≤ `exp`) cachen.

## Zusammenfassung

- S1: 0
- S2: 1 (verbrauchte `email_verifications`-Zeilen werden nie gelöscht + fehlender Index auf `session_id`/`code`)
- S3: 1 (SMTP-Transport ohne Pooling/Timeouts blockiert `/hhttps/email/send`)
- S4: 4 (`sessions.delete` fehlt, Stats-Hot-Row, sequentielle Roundtrips in `/token/refresh`, JWT-Verify auf statischen Assets)

Gesamteindruck: Die AP3-Pfade sind DB-seitig sauber aufgebaut — alle Session-, Challenge-, Anchor- und Claims-Cache-Zugriffe laufen über Primärschlüssel oder vorhandene Indizes, das 5-Minuten-Cleanup deckt Sessions, Challenges (inkl. `email:<sid>`-Kontexte), Tokens und den Claims-Cache ab, und `bindSessionToEmailAnchor` parallelisiert bereits die unabhängigen Writes. Es gibt keine In-Memory-Caches ohne Eviction, keine blockierenden Sync-Operationen im Hauptpfad (außer dem `existsSync`-Fallback) und keine Pool-Client-Leaks (durchgängig `pool.query`). Die eine relevante Schwachstelle ist die Kombination aus nie gelöschten verbrauchten E-Mail-Verifikationen und indexlosen Lookups auf genau dieser Tabelle — sie sitzt auf dem verpflichtenden ersten Schritt jedes Logins und wird mit der Nutzerzahl schleichend teurer. Der SMTP-Versand ohne Timeouts ist das zweite Thema mit realer Auswirkung auf die Antwortzeit des Sign-ins.
