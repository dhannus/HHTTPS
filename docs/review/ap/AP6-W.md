### [S2] [Wartbarkeit] server/scripts/install-pg.sh:L72-82 — Die dokumentierten Installationsskripte spielen nur schema.sql ein; ein frisch aufgesetzter Server bootet damit nicht
**Begründung:** `install-pg.sh` (L73, L79-81) und `scripts/deploy-all.sh` (L145-152) laden ausschließlich `sql/schema.sql`. `schema.sql` enthält aber nur den v4.1-Stand (credentials … stats, L11-189); `signatures`, `reserved_slugs`, `oauth_clients`, `authorization_codes`, `connected_platforms`, `admins`, `client_stats_daily`, `admin_actions`, `external_verification_anchors`, `github_oauth_pending`, `workload_identities` existieren nur in den neun manuell einzuspielenden `migration-*.sql`. Kein Skript und keine `package.json`-Task spielt diese ein (README L286 sagt lediglich „must be applied too“, ohne Reihenfolge). Beim Boot läuft dann `db.ensureBootSchema()` (server.js L4800): `phase8SchemaApplied()` liefert `false`, die Phase-8-DDL enthält `ALTER TABLE authorization_codes ADD COLUMN …` (migration-phase-8 L67-70) → `42P01 relation "authorization_codes" does not exist` → `process.exit(1)`.
**Auswirkung:** Wer nach README/Skripten neu installiert (oder eine Testumgebung nach `install-pg.sh` aufsetzt), bekommt einen Server, der sofort mit „Boot schema migration failed“ abbricht; die Ursache (fehlende Vor-Migrationen) ist aus der Meldung nicht ersichtlich. Jede neue Umgebung erfordert Reverse-Engineering der Migrationsreihenfolge.
**Empfehlung:** Einen einzigen Migrationslauf einführen (z. B. `scripts/migrate.js`, das `package.json` L9 ohnehin schon referenziert): Ledger-Tabelle `schema_migrations`, alle `sql/*.sql` in fester Reihenfolge, Aufruf aus `install-pg.sh`/`deploy-all.sh` und optional aus `main()`. Bis dahin mindestens die Reihenfolge im README auflisten und in `install-pg.sh` einspielen.

### [S3] [Wartbarkeit] server/db.js:L372-383 — Vier konkurrierende Schema-Mechanismen (schema.sql + manuelle Migrationen, `ensureCodeColumn` bei Import, `BOOT_DDL_FILES`, Privacy-Pass-`MIGRATIONS`) ohne gemeinsames Ledger
**Begründung:** (1) `ensureCodeColumn()` feuert als Fire-and-forget beim Modul-Import (L383, Fehler werden nur geloggt); die Spalte `email_verifications.code` steht weder in `schema.sql` noch in einer Migrationsdatei (`grep 'ADD COLUMN IF NOT EXISTS code' sql/` = leer). (2) `BOOT_DDL_FILES` (L432-439) läuft mit Applied-Check und bricht den Boot bei Fehler ab. **Auswirkung:** Niemand kann aus dem Code ablesen, welche Spalte woher kommt; Schemaänderungen werden je nach Laune in einen der vier Pfade gelegt; unterschiedliche Fehlersemantik (abbrechen vs. weiterlaufen) macht Boot-Verhalten schwer vorhersehbar. **Empfehlung:** `ensureCodeColumn` in eine Datei `migration-phase-x-email-code.sql` überführen und in `BOOT_DDL_FILES` aufnehmen; Privacy-Pass-Migrationen ebenfalls als Einträge in `BOOT_DDL_FILES` (oder in das unter S2 vorgeschlagene Ledger) statt eigener Schleife; nur noch ein Mechanismus mit einheitlicher Abbruchsemantik.

## Zusammenfassung

Anzahl je Severity: **S1: 0 · S2: 1 · S3: 14 · S4: 7** (22 Findings).

Gesamteindruck: `db.js` ist als dünne, gut kommentierte SQL-Schicht solide lesbar, leidet aber an inkonsistenten Rückgabeformaten, kopierten JSON-Parsern und totem Cleanup-Code. Das eigentliche Wartbarkeitsproblem des Arbeitspakets ist das Schema-Management: vier parallele Mechanismen ohne Ledger, Installationsskripte, die nur `schema.sql` laden und damit keinen bootfähigen Server erzeugen, sowie eine Sammlung von Betriebsskripten, die teils obsolet sind (ZIP-Migration, Live-Patcher, Privacy-Pass-Deploy) und Provisionierung/Env-Parsing mehrfach mit abweichender Semantik implementieren. CI prüft nur Syntax; Tests, Lint und Audit laufen ausschließlich lokal.
