## 3. Urteil

**ABGENOMMEN** — 26/26 Kriterien PASS, 0 FAIL, 0 OFFEN.

Kennzeichnungen (gemäß Spec-Wortlaut bewertet, aber mit eingeschränkter Nachweisart):
- AK-4, AK-5, AK-21: WebAuthn-Zeremonie ohne Authenticator nicht ausführbar → Unit-Test + Code-Inspektion (AK-5) bzw. HTTP bis zur Options-Ausgabe + Code-Inspektion (AK-4) bzw. simulierte Credential (AK-21). Der SHALL-Wortlaut ist jeweils durch die reine Funktion (`resolvePasskeySession`) und ihre Verdrahtung belegt.
- AK-14, AK-15: nur statische Prüfung des HTML/Scripts — so in tasks.md T7 vorgesehen (S-8).
- AK-9: PASS mit Vorbehalt. Im spezifizierten Pfad erfüllt; der Age-only-Pfad (kein AK) liefert ein `token/refresh`-Token ohne `pseudonym`. Das ist keine Umsetzungslücke, sondern eine Spec-Lücke (S-5/S-6), die Daniel entscheiden muss (Empfehlung B-2). Fällt die Entscheidung auf „Age wird gegated“, bleibt AK-9 unverändert gültig und wird durch den Gate-Fix vollständig; fällt sie auf „Age ist Ausnahme“, ist AK-9 auf E-Mail-verankerte Identitäten einzuschränken.

Der Befund B-1 (Server-Crash bei `/hhttps/machine/register`) ist kein Kriterium dieser Spec und vorbestehend (fehlende Spalte `key_jkt`), blockiert die Abnahme des Features daher nicht — er ist aber deploy-relevant (DoS über einen Request) und sollte vor Gate 2 / MR separat behoben werden, s. Abschnitt 4.

## 4. Empfehlungen für Folge-Iteration

### 4.1 Befunde aus dem Testprotokoll

**B-1 — `/hhttps/machine/register` beendet den Server-Prozess (hoch, vorbestehend, außerhalb Scope).**
`server/db.js::machineOperators.create` (Z. 563) schreibt `machine_operators.key_jkt`; keine Migration unter `server/sql/` legt die Spalte an; die Route (`server.js` Z. 3758) hat keinen `try/catch` → unbehandelte Rejection, Prozess-Exit. Nicht Teil von AK-1..26 und nicht durch dieses Feature verursacht (der Pfad ist nur jetzt, nach E-Mail-Bestätigung, in der Testreihenfolge sichtbar geworden). Empfehlung: eigener Bugfix vor Deploy — `ALTER TABLE machine_operators ADD COLUMN IF NOT EXISTS key_jkt TEXT` als Migration, `try/catch` in der Route, `process.on('unhandledRejection')`-Schutz. Test `I/acceptance.test.mjs::B-1 (todo)` danach von `todo` auf regulär umstellen.

**B-2 — Age-Endpunkte ohne E-Mail-Gate (mittel) — Spec-Entscheidung für Daniel.**
Sachlage: requirements.md §2 Scope sagt „Alle anderen Methoden (Passkey, GitHub, EUDI, **Alter**) sind erst nach E-Mail-Verifikation nutzbar (UI ausgegraut/nicht klickbar; **Backend lehnt ab**)“. AK-14 setzt das für die UI um (Button `#m-age` disabled). Für das Backend existiert aber kein AK für `/hhttps/age/direct` (Z. 3332) und `/hhttps/age/upgrade` (Z. 3180) — AK-10..13 nennen nur WebAuthn, GitHub, EUDI, `role/declare`. Beobachtet: beide Endpunkte stellen ohne E-Mail ein Token aus; `age/direct` erzeugt dabei eine neue Identität ohne Anker, deren Refresh-Token über `token/refresh` ein Token ohne `pseudonym` liefert (Wortlaut-Gegenbeispiel zu AK-9) und das per `oauth/approve` bei einer Plattform einlösbar ist (Login ohne E-Mail, ohne `preferred_username`).
Das ist ein Widerspruch zwischen Scope-Text und AK-Liste, den ich als Spec-Autor zu verantworten habe. Zwei Optionen:
- **Option A (Scope-Text gilt):** neue Kriterien „AK-12b: IF eine Session ohne bestätigte E-Mail `/hhttps/age/upgrade` aufruft, THEN 403 `email_verification_required`“ und „AK-12c: `/hhttps/age/direct` SHALL nur mit `sessionId` einer E-Mail-bestätigten Session ein Token ausstellen (403 sonst)“. Dann werden die drei `SPEC-GAP`-todo-Tests zu FAIL → Fix in `server.js` (Gate wie Z. 3503) → AK-9 ohne Vorbehalt.
- **Option B (Age ist Ausnahme, z. B. weil `age/direct` ein interner Verifier-Callback ist):** AK-9 einschränken auf „Token einer E-Mail-verankerten Identität“, Ausnahme in §2 dokumentieren, Loopback-/Secret-Schutz für `age/direct` als NFA festhalten (heute schützt allein `EUDI_VERIFIER_SECRET`, keine 127.0.0.1-Prüfung), und festlegen, ob ein Age-only-Token bei `oauth/approve` zulässig ist.
Meine Empfehlung: Option A — sie entspricht dem freigegebenen Scope-Text und dem Nicht-Ziel „kein Login ohne E-Mail“.

**B-3 — `confirm-code` konsumiert den Code vor der Session-Prüfung (niedrig).** Reihenfolge `verifyEmailCode()` → `sessions.get()` in `server.js` Z. 2869 ff.; bei abgelaufener Session ist der Code verbraucht, Nutzer muss neu senden. Empfehlung: Session zuerst prüfen (kein AK betroffen).

**B-4 — Uneinheitliche Statuscodes für unbekannte/abgelaufene Session (niedrig).** 400/401/404 je Endpunkt. Empfehlung: einheitlich 401 `invalid_session` als Spec-Kriterium in der nächsten Iteration (siehe S-2), rein additiv bei Bestandsclients nicht kritisch, aber Breaking für Fehlerbehandlung → bewusst entscheiden.

**B-5 — `register/finish` prüft keine Session (niedrig, Defence in depth).** AK-4 ist erfüllt (Challenge nur dem Aufrufer von `register/start` bekannt, 120 s TTL). Empfehlung: `sessionId` auch in `finish` verlangen und gegen den Challenge-Schlüssel prüfen.

**B-6 — `/userinfo` gibt für Maschinen kein `actor_type` aus (Beobachtung).** ID-/Access-Token tragen `actor_type:'bot', human:false`, `/userinfo` nicht. Empfehlung: Konsistenz herstellen; zusammen mit S-7 spezifizieren.

### 4.3 Annahmen aus requirements.md §6 — Bestätigung durch Daniel erbeten

1. **„Issuer“ = OAuth-Client-Plattform** (ask.iamhmn.org, WordPress-Plugin). Die Umsetzung liefert `email`, `preferred_username` und die Methoden-Flags an die Plattform (ID-Token, Access-Token, `/userinfo`). Wenn mit „Issuer“ HHTTPS selbst gemeint war, wäre nur die Anzeige/Speicherung auf HHTTPS-Seite betroffen — dann bitte melden.
2. **`email` für Bestandsclients per Migration in `allowed_scopes`.** Ursprüngliche Annahme: „damit die Übertragung sofort möglich ist“. Nach Review-Fix F-7 (P-2/W-11/S-10) läuft das `UPDATE oauth_clients … += "email"` **nicht mehr beim Boot**, sondern nur im OPERATOR-Abschnitt der Migrationsdatei, den der Betreiber einmalig per `psql` ausführt. Konsequenz: Bestandsclients (z. B. ask.iamhmn.org) erhalten die E-Mail erst, nachdem der Operator-Block ausgeführt wurde — bis dahin antwortet `authorize`/`approve` mit `invalid_scope` (AK-19), sobald die Plattform `email` anfordert. Neue Clients bekommen `email` per Default. Das ist die sicherere Variante (Opt-out möglich); der Deploy-Plan muss den Operator-Schritt aber enthalten (README/CHANGELOG nennen ihn).
